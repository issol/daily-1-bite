> **2026-08-18 업데이트.** 이 글을 발행하고 약 2주 뒤, 이 블로그의 구글 색인은 122페이지에서 **0**이 됐습니다. 아래 1부는 당시의 기록 그대로 두고(무엇을 믿고 있었는지도 기록이니까요), 그 뒤에 일어난 4개월간의 붕괴와 복구 과정을 이 글 하단의 **2부**에 실측 데이터로 적었습니다. 지금의 저에게 더 쓸모 있는 건 1부가 아니라 2부입니다.

처음엔 반신반의했어요. "SEO 최적화하면 정말 방문자가 늘어날까?" 블로그 시작한 지 6개월, 하루 방문자 수가 고작 30명 정도였거든요. 그런데 3주간의 집중 최적화 작업 후, 지금은 하루 평균 90명이 들어와요. 어떻게 했는지 타임라인별로 정리해드릴게요.

## 1주차: 구조화 데이터 추가 & 메타 태그 최적화

첫 주에는 기본 중의 기본부터 손봤어요.

### 1. 메타 태그 다시 쓰기

기존에는 그냥 대충 "블로그 제목 - 부제목" 이런 식으로만 써놨더라고요. 이걸 완전히 갈아엎었어요.

- **타이틀 태그**: 40-60자 사이로 맞추고, 핵심 키워드를 앞쪽에 배치
- **메타 디스크립션**: 120-158자로 작성, 클릭하고 싶게 만드는 문구 추가
- **키워드 앞배치 전략**: "방법", "후기" 같은 검색 의도 단어를 제목 앞부분에

예를 들어 이런 식이에요.

| 변경 전 | 변경 후 |
| --- | --- |
| 블로그 수익화 - 매일 한입 | 블로그 수익화 방법 3가지: 3개월 만에 월 50만원 달성한 후기 |
| AI 관련 포스팅입니다. | ChatGPT 활용법 5가지로 업무 시간 50% 단축한 실제 사례 (무료 템플릿 포함) |

### 2. 구조화 데이터(Schema Markup) 추가

이게 진짜 효과가 컸어요. JSON-LD 형식으로 Article 스키마를 모든 포스팅에 추가했어요. 구글이 내 글을 "뉴스 기사" 수준으로 인식하기 시작하더라고요.

```html
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "포스팅 제목",
  "author": {
    "@type": "Person",
    "name": "작성자 이름"
  },
  "datePublished": "2026-01-15"
}
</script>
```

### 1주차 결과

정직하게 말씀드리면, 1주차에는 변화가 거의 없었어요. 구글 서치 콘솔에서 "처리 중"만 뜨더라고요. 참을성이 필요한 시기예요.

## 2주차: 내부 링크 구조 개선 & 이미지 최적화

2주차부터 본격적으로 손이 많이 갔어요.

### 1. 내부 링크 전략적으로 깔기

기존 포스팅 50개를 전부 열어서 관련 글끼리 연결했어요.

- 한 포스팅당 최소 2-3개의 내부 링크 추가
- 앵커 텍스트에 키워드 자연스럽게 포함 (예: "이 방법"이 아니라 "ChatGPT 프롬프트 작성법")
- "시리즈" 형태로 묶을 수 있는 글들은 상단에 목차 박스 추가

이게 생각보다 효과가 좋았어요. 방문자가 한 페이지만 보고 나가는 게 아니라, 평균 2.3페이지를 보게 됐거든요. 구글이 "오, 이 블로그는 양질의 연관 콘텐츠가 많네?"라고 판단하는 것 같더라고요.

### 2. 이미지 최적화 (이게 진짜 중요)

블로그에 올린 이미지들이 용량이 너무 컸어요. 스마트폰으로 찍은 사진을 그냥 올렸거든요.

- 모든 이미지 WebP 포맷으로 변환 (TinyPNG 사이트 이용)
- 파일명을 "IMG_1234.jpg"에서 "chatgpt-prompt-example.webp"로 변경
- alt 텍스트 꼼꼼하게 작성 (검색 노출용)

### 실패한 시도도 솔직하게 공유

2주차에 "키워드 밀도 10%가 좋다"는 글을 보고 따라했다가 오히려 순위가 떨어졌어요. 구글이 키워드 스터핑으로 판단한 것 같더라고요. 자연스럽게 쓰는 게 답이에요.

### 2주차 결과

- 일 방문자: 30명 → 52명 (73% 증가)
- 페이지뷰: 35 → 120 (243% 증가)
- 평균 체류 시간: 42초 → 1분 38초

드디어 변화가 느껴지기 시작했어요!

서치 콘솔 "실적" 탭에서 "노출은 많은데 클릭이 없는 검색어"를 찾았어요. 이런 키워드들은 제목이나 설명이 별로였던 거예요. 해당 포스팅 10개를 리라이팅했더니 다음날부터 클릭이 들어오기 시작했어요.

- 구글 유입 비율: 23% → 67%
- 블로그 체류 시간: 42초 → 2분 14초

## 4주차: GEO(생성형 엔진 최적화) 실험

3주차가 끝나고 저는 좀 더 욕심이 생겼어요. 구글 검색 최적화(SEO)는 어느 정도 궤도에 올랐으니, 이제 AI 검색 시대에 맞는 전략을 실험해보자고요.

### GEO란 무엇인가요?

GEO는 **Generative Engine Optimization**, 즉 생성형 엔진 최적화예요. ChatGPT Search, Perplexity, Google AI Overviews, Claude처럼 AI가 직접 답변을 생성해주는 검색 엔진에 최적화하는 작업이에요.

기존 SEO와 GEO의 핵심적인 차이점이 있어요.

| 비교 항목 | SEO (구글 전통 검색) | GEO (AI 검색 엔진) |
| --- | --- | --- |
| 목표 | 검색 결과 상위 노출 | AI 답변에 인용(citation)되기 |
| 평가 방식 | 링크, 키워드, 권위도 | 명확성, 직접 답변, 구조화 |
| 결과 확인 | 순위 및 클릭수 | AI가 내 글을 인용했는지 여부 |
| 최적화 단위 | 페이지 전체 | 단락, 문장 수준 |

AI 검색 엔진은 페이지를 "읽는" 방식이 달라요. 구글 봇은 링크 구조와 키워드를 중시하지만, AI 엔진은 **직접적인 답변**, **명확한 인용 근거**, **구조화된 데이터**를 찾거든요. 쉽게 말하면, AI가 "이 문장을 그대로 인용해도 되겠다"고 판단할 수 있는 글을 써야 해요.

### 제가 실제로 바꾼 것 5가지

#### 1. 모든 포스팅 상단에 TL;DR / 핵심 요약 추가

AI 검색 엔진은 글의 첫 단락에서 핵심 내용을 찾아요. 그래서 모든 포스팅 맨 위에 "이 글 한 줄 요약"을 추가했어요.

```
**핵심 요약**: ChatGPT API를 활용해 자동화 스크립트를 만드는 방법을 3단계로 정리합니다.
비용은 월 $3 이하, 구현 시간은 2시간 내외입니다. (2026년 4월 기준)
```

이렇게 하면 Perplexity 같은 AI 검색이 내 글을 참조할 때 이 요약문을 그대로 인용할 가능성이 높아져요.

#### 2. H2 헤딩을 "직접 답변형"으로 재작성

기존에는 "X란 무엇인가"처럼 질문 형식으로 헤딩을 썼는데, "X는 Y입니다"처럼 답변 자체를 헤딩으로 바꿨어요.

| 변경 전 | 변경 후 |
| --- | --- |
| ChatGPT API란 무엇인가 | ChatGPT API는 OpenAI의 언어 모델을 코드로 호출하는 인터페이스입니다 |
| 블로그 수익화 방법 | 블로그 수익화의 3가지 핵심 경로: 광고, 제휴, 디지털 상품 |

AI 엔진은 헤딩을 그대로 답변에 쓰는 경우가 많아요. 헤딩 자체가 답변이 되면 인용률이 올라가더라고요.

#### 3. FAQ 섹션 추가 (Q&A 포맷)

AI 검색 엔진이 가장 좋아하는 형식 중 하나가 명확한 Q&A예요. 모든 포스팅 하단에 "자주 묻는 질문" 섹션을 추가했어요.

```markdown
## 자주 묻는 질문 (FAQ)

**Q. ChatGPT API 무료 버전이 있나요?**
A. 2026년 현재 OpenAI는 무료 API를 제공하지 않습니다. 신규 가입 시 $5 크레딧이 주어지며, 이후 사용량 기반 과금이 적용됩니다.

**Q. 개인 블로거도 API를 사용할 수 있나요?**
A. 네, 신용카드 등록만 하면 누구나 사용 가능합니다. 월 $5-10 수준의 저비용으로 충분히 활용할 수 있어요.
```

Perplexity는 Q&A 구조를 특히 잘 인용해요. 실제로 이 변경 후 2주 뒤에 제 FAQ가 Perplexity 답변에 등장한 걸 확인했어요.

#### 4. 모든 주장에 날짜/버전 명시

"ChatGPT는 GPT-4 모델을 사용합니다"보다 "ChatGPT는 2026년 4월 기준 GPT-4o 모델을 기본으로 사용합니다"가 AI 인용에 훨씬 유리해요. AI 엔진은 신뢰할 수 있는 정보인지 판단할 때 날짜 정보를 중요하게 봐요.

모든 글에서 시점이 있는 정보에는 반드시 "(2026년 4월 기준)" 같은 날짜를 붙이기 시작했어요.

#### 5. 참고 자료 섹션 구조화

단순히 링크를 나열하는 게 아니라, 각 출처의 발행 기관과 날짜를 명시하는 방식으로 바꿨어요.

```markdown
## 참고 자료
- [OpenAI API 가이드](https://platform.openai.com/docs) — OpenAI, 2026년 공식 문서
- [구글 AI Overviews 원리 설명](https://blog.google/...) — Google, 2025년 12월 발행
```

AI 엔진은 인용 출처를 사용자에게 보여줘야 해서, 출처가 명확한 글을 선호해요. 제 글이 출처를 명확히 달고 있으면, AI가 그 출처 체인의 일부로 포함시킬 가능성이 높아지거든요.

### 2주간의 GEO 실험 결과: 솔직하게

정직하게 말씀드릴게요. **GEO는 SEO보다 결과가 훨씬 느려요.**

2주 실험 기간 동안 제가 직접 Perplexity에서 블로그 주제 키워드를 검색해봤을 때:
- 첫 주: 내 블로그 글은 전혀 인용되지 않음
- 2주 후: 특정 FAQ 섹션이 있는 포스팅 1개가 Perplexity 답변에 인용되기 시작

Google AI Overviews에서는 2주 안에 뚜렷한 변화를 확인하기 어려웠어요. 다만, 서치 콘솔에서 "AI 개요" 관련 노출이 소폭 늘었다는 신호는 있었어요.

**솔직한 평가**: GEO는 3-6개월을 봐야 하는 장기 게임이에요. SEO가 "구글 알고리즘을 설득하는 것"이라면, GEO는 "AI가 신뢰할 수 있는 정보원으로 내 블로그를 학습시키는 것"에 가까워요. 빠른 결과를 원한다면 SEO에 집중하고, GEO는 지금부터 꾸준히 쌓아가는 전략으로 접근하는 게 맞아요.

### GEO 체크리스트 (5가지)

새 글 발행 전 반드시 확인하세요.

- [ ] **핵심 요약 추가**: 글 상단 3문장 이내로 "이 글이 답하는 것"을 명확히
- [ ] **직접 답변형 헤딩**: H2/H3이 질문이 아닌 답변 형태인지 확인
- [ ] **FAQ 섹션**: 최소 3개의 Q&A 추가 (예상 검색 질문 기반)
- [ ] **날짜/버전 명시**: 시점이 있는 모든 주장에 "(YYYY년 MM월 기준)" 표기
- [ ] **참고 자료 구조화**: 출처명 + 기관명 + 발행 연도 함께 표기

블로그 포스팅을 발행하기 전, 이 10가지를 확인해보세요. SEO와 GEO를 동시에 잡을 수 있어요.

| 항목 | SEO 이유 | GEO 이유 |
| --- | --- | --- |
| 타이틀 태그 40-60자, 키워드 앞배치 | 검색 결과 CTR 향상 | AI가 제목에서 주제를 빠르게 파악 |
| 메타 디스크립션 120-158자 작성 | 클릭률 직접 영향 | AI Overviews 스니펫 소스로 활용됨 |
| H1-H2 계층 구조 정리 | 구글 크롤러 문서 이해 | AI가 섹션별 답변을 추출하기 용이 |
| 글 상단 TL;DR 요약 추가 | 체류 시간 및 이탈률 개선 | AI 인용 시 핵심 문장으로 사용됨 |

| FAQ 섹션 추가 | 지식 그래프 박스 노출 가능성 | AI 검색 인용률 가장 높은 형식 |
| 날짜/버전 명시 | 최신성 신호, 재크롤링 촉진 | AI가 정보 신뢰도 판단 시 우선 참조 |
| 참고 자료 출처 명시 | E-E-A-T(전문성) 신호 강화 | AI 인용 체인에 포함될 가능성 상승 |

## 개인적으로 가장 효과가 컸던 것

3주간 작업하면서 느낀 건데, **구조화 데이터(Schema Markup)**가 생각보다 엄청 중요하더라고요. 이거 넣고 나서 구글 검색 결과에 별점, 작성일, 썸네일이 풍부하게 표시되기 시작했어요. 당연히 클릭률이 올라갈 수밖에 없죠.

그리고 의외로 **이미지 최적화**도 큰 영향을 미쳤어요. 페이지 로딩 속도가 3.2초에서 1.1초로 줄어들었거든요. 구글이 "Core Web Vitals" 점수를 높게 줬더라고요.

예상 못 했던 발견도 있었어요. **리다이렉트 문제를 정리한 게 생각보다 임팩트가 컸어요.** 구글 서치 콘솔에서 "리다이렉션 오류"로 잡혀 있던 URL 44개를 수정했는데, 그 다음 주에 크롤링 빈도가 눈에 띄게 올라갔거든요. 구글이 리다이렉트를 따라가면서 크롤링 예산을 낭비하고 있었던 거예요. 오류를 잡고 나니까 멀쩡한 페이지들이 훨씬 빨리 인덱싱됐어요.

또 하나, **타이틀 태그 수정의 효과가 빠르게 나타났어요.** 메타 디스크립션 수정 후 평균 3-5일 안에 CTR 변화를 서치 콘솔에서 확인할 수 있었는데, 이게 체감 속도로 가장 빠른 변화였어요. 구조화 데이터나 내부 링크는 몇 주가 걸리는 반면, 타이틀/디스크립션은 "지금 당장 수정하면 이번 주 안에 효과 보는" 액션이에요. 급할수록 여기서 시작하세요.

## 2부: 그리고, 색인이 0이 됐다

여기까지가 2026년 3월의 저였습니다. "같이 성장해봐요"라고 쓴 지 2주 뒤, 이 블로그는 구글 검색에서 사라졌습니다.

지금부터는 2026년 8월의 제가 씁니다. 아래 숫자는 전부 이 블로그의 실제 구글 서치 콘솔 데이터이고, 날짜와 원인은 저장소 커밋 기록으로 교차 확인한 것입니다. 위 1부처럼 "이렇게 하면 됩니다"가 아니라, **무엇이 틀렸는지**의 기록입니다. SEO 실패 사례는 검색해도 잘 안 나옵니다. 다들 성공기만 쓰니까요. 그래서 이 2부가 1부보다 희소한 정보라고 생각합니다.

### 타임라인: 122 → 0 → (아직) 2

| 날짜 | 사건 | 색인된 페이지 |
| --- | --- | --- |
| 2026-03-29 | 이 글(1부) 발행 | 상승 중 |
| 2026-04-14 | 다국어(i18n) 라우팅 개편 + AdSense 신청 | **122 (최고점)** — 여기서부터 급락 |
| 2026-05-02 | 색인 사실상 소멸, 노출 0 시작 | 0~1 |
| 2026-05-06 | 발행일 일괄 "교정" (역효과 — #4에서 설명) | 0~1 |
| 2026-07-23 | 원인 확정, 저품질 37편 noindex, 정책 변경 동결 | 0~1 |
| 2026-08-03 | 호스팅 이전 (크롤 응답 274ms → 72ms) | 0~1 |
| 2026-08-10 | URL 구조를 4월 이전으로 원복, i18n 제거 | 1 |
| 2026-08-18 | 현재 | **2** (노출 0) |

넉 달 동안 색인 0. 1부에서 자랑한 "일 방문자 92명"은 당연히 함께 사라졌습니다. 무엇이 틀렸는지 다섯 가지로 정리합니다.

### 틀린 것 #1 — 사고는 '개선'하다가 난다

4월 14일, 블로그를 다국어로 확장하면서 URL을 `/ko/...` 구조로 바꿨습니다. 그 자체는 흔한 개편입니다. 문제는 **canonical 태그를 만드는 코드가 새 URL 구조를 몰랐다는 것**입니다. 새 페이지들이 "이 페이지의 정본은 `/blog/...`(prefix 없는 구 URL)"라고 선언했는데, 그 구 URL은 이미 301로 새 URL을 가리키고 있었습니다.

구글 입장에서 보면: A페이지가 "정본은 B"라고 하는데, B에 가보면 "A로 가라"는 리디렉션이 있습니다. 순환하는 신호입니다. 구글은 이런 경우 둘 다 버립니다. 대량 탈락은 이렇게 시작됐습니다.

교훈: **라우팅을 개편하면 canonical 생성 코드는 조용히 낡습니다.** 공식 문서는 "canonical을 정확하게 설정하라"고만 하지, 이게 라우팅 변경 때마다 다시 깨질 수 있는 살아있는 코드라는 건 말해주지 않습니다. 개편 직후에는 배포된 페이지의 canonical을 **실제로 열어서** 확인해야 합니다.

### 틀린 것 #2 — 여섯 번의 수정이 여섯 번의 리셋이었다

사고를 인지한 뒤 4월부터 7월까지 canonical, robots, noindex, hreflang, sitemap 정책을 **여섯 차례 이상** 고쳤습니다. 각각의 수정은 개별적으로는 타당했습니다. 그런데 색인은 돌아오지 않았습니다.

이유를 나중에야 이해했습니다. 구글이 사이트 신뢰도를 재평가하는 데는 수 주가 걸리는데, **그 사이에 신호를 또 바꾸면 재평가가 처음부터 다시 시작됩니다.** 여섯 번 고쳤다는 건 재평가를 여섯 번 리셋했다는 뜻입니다. 더 나쁜 건, 어떤 수정이 효과가 있었는지 영원히 알 수 없게 됐다는 겁니다. 변인이 여섯 개면 실험이 아닙니다.

그래서 7월 23일에 반대로 갔습니다: **색인 관련 정책을 문서로 못 박고 몇 주간 변경을 동결**했습니다. 지표가 답답해도 손대지 않는 것이 손대는 것보다 나았습니다.

### 틀린 것 #3 — 아무도 HTTP 응답 헤더를 보지 않는다

가장 오래 숨어 있던 문제입니다. 다국어 프레임워크(next-intl)가 모든 페이지에 `Link:` 응답 헤더로 hreflang을 **자동 송출**하고 있었습니다. HTML 안의 `<link>` 태그와 내용이 달랐고, 헤더 쪽 `x-default`는 리디렉션되는 레거시 URL을 가리켰습니다. 페이지마다 "정본이 무엇인가"에 대한 모순된 선언이 두 벌씩 나가고 있던 겁니다.

이걸 **3개월간 발견하지 못했습니다.** 브라우저 개발자 도구의 Elements 탭에는 HTML만 보이지 응답 헤더의 hreflang은 안 보이니까요. 발견은 결국 터미널에서였습니다:

```bash
$ curl -sI https://daily1bite.com/blog/seo/blog-seo-3-weeks | grep -i "^link"
# 당시: Link: <https://daily1bite.com/blog/...>; rel="alternate"; hreflang="x-default" ← 리디렉션되는 URL
# 지금: (출력 없음 — 2026-08-18 실측, 정상)
```

교훈: 검증 루틴에 렌더링된 HTML만이 아니라 `curl -sI`를 넣으세요. 프레임워크는 여러분이 모르는 헤더를 내보냅니다.

### 틀린 것 #4 — 날짜를 '바로잡다가' 더 나쁜 신호를 만들었다

5월 6일, 과거 글들의 발행일이 부정확한 걸 발견하고 git 기록 기준으로 일괄 교정했습니다. 정직해지려는 조치였는데, 결과적으로 **56편의 발행일이 2026-03-29 하루로 몰렸습니다.** sitemap과 구조화 데이터(JSON-LD)의 `datePublished`가 "하루에 56편 동시 발행"이 된 겁니다.

이건 구글의 [스팸 정책](https://developers.google.com/search/docs/essentials/spam-policies)이 말하는 확장 콘텐츠 악용(scaled content abuse)의 전형적인 지문입니다. 날짜 조작을 없애려던 조치가 더 나쁜 조작처럼 보이는 신호를 만들었습니다.

교훈: **발행일(`date`)은 어떤 이유로도 소급 수정하지 않습니다.** 내용을 갱신했으면 `updated`(dateModified) 필드를 씁니다. 이 글도 그렇게 하고 있습니다 — 상단의 date는 2026-03-29 그대로이고, 이 2부는 updated로만 표시됩니다.

### 틀린 것 #5 — 진짜 문제는 기술이 아니었다

위 네 가지를 다 고치고도 색인은 돌아오지 않았습니다. 서치 콘솔의 미색인 사유 분포가 답을 말해주고 있었습니다: 지배적인 사유가 robots 차단도, 리디렉션 오류도 아닌 **"크롤링됨 – 현재 색인이 생성되지 않음" 185건**이었습니다.

이 상태의 의미는 명확합니다. 구글이 페이지를 **읽는 데 성공했고, 읽고 나서 색인할 가치가 없다고 판단**한 겁니다. 기술 문제가 아니라 품질 판정입니다. 공교롭게 같은 시기에 AdSense 심사도 저품질 사유로 반려됐습니다. 서로 다른 두 시스템이 같은 판정을 내린 거죠.

당시 이 블로그는 매일 AI 뉴스 요약을 자동 발행하고 있었습니다. 글 길이는 평균 1,300단어로 thin하지 않았지만, **다른 데서 복제할 수 없는 정보가 없었습니다.** 기술 SEO를 아무리 다듬어도 이 판정은 뒤집히지 않습니다. 1부의 체크리스트가 전부 무력해지는 지점입니다.

### 복구 로그: 그래서 무엇을 했나

- **저품질 37편 noindex** — 고유 가치가 있는 글만 색인 대상으로 남겼습니다. 색인 대상을 줄이는 게 늘리는 것보다 먼저였습니다.
- **정책 동결** — #2의 교훈. 변경을 멈추고 관찰 기간을 확보했습니다.
- **호스팅 이전(8/3)** — 서치 콘솔 크롤링 통계 실측으로 크롤 평균 응답이 **274ms → 72ms**, 약 4배 빨라졌습니다. 응답 바이트를 이전 호스팅과 대조해 동등성을 확인하고 옮겼습니다(정책 변경 0).
- **URL 구조 원복(8/10)** — `/ko/...`를 버리고 색인이 122였던 시절의 URL로 되돌렸습니다. 구 URL은 전부 홉 1회짜리 301입니다.
- **부수 발견**: 크롤 응답 코드 90일 누적에서 302(임시 리디렉션)가 4.17%나 됐는데, 원인은 i18n 미들웨어가 미등록 경로를 전부 307로 `/ko/<경로>`에 보내며 만든 `307 → 404` 체인이었습니다. i18n 제거로 함께 소멸했고, 현재 임시 리디렉션은 실측 0건입니다.

### 오늘의 발견 — 구글은 오류가 났던 URL에 다시 오지 않는다

1부에서 "리디렉션 오류 44개를 고쳤더니 크롤링이 늘었다"고 썼습니다. 오늘은 그 반대편을 배웠습니다. 서치 콘솔에 리디렉션 오류 8건이 남아 있는데, 최종 크롤 날짜가 전부 **2026년 4월 11~15일** — 사고 당시입니다. 오늘 8개 URL을 전부 실측하니 모두 정상 200 응답입니다:

```bash
$ curl -s -o /dev/null -w "%{http_code}\n" \
    https://daily1bite.com/blog/ai-tutorial/claude-code-april-2026-update
200   # 나머지 7건도 동일 (2026-08-18 실측)
```

즉 오류는 4개월 전에 고쳐졌지만, **구글이 4개월간 한 번도 재방문하지 않아** 오류 기록이 박제돼 있는 겁니다. 한 번 오류가 났던 URL은 크롤 우선순위가 바닥까지 떨어져서, 고쳐놓고 기다리는 것만으로는 안 사라집니다. 서치 콘솔에서 해당 문제의 **"유효성 검사 시작"** 버튼을 눌러 재크롤을 명시적으로 요청해야 합니다.

### 하지 말아야 할 것 — 1부의 체크리스트를 뒤집으며

1부는 "해야 할 것 10가지"로 끝났습니다. 4개월을 겪은 지금은 **하지 말아야 할 것**이 더 중요하다고 생각합니다.

- **색인이 잘 되고 있다면 URL 구조를 건드리지 마세요.** 다국어든 리브랜딩이든, 그 이득이 재평가 리셋 비용보다 큰 경우는 드뭅니다.
- **사고가 나면 수정을 한 번에 묶고, 이후 수 주간 관찰만 하세요.** 찔끔찔끔 여섯 번 고치는 건 여섯 번 리셋하는 겁니다.
- **발행일을 소급 수정하지 마세요.** 어떤 선의로도요. 갱신은 dateModified로.
- **구글이 301을 크롤한 뒤에는 되돌리지 마세요.** 롤백이 더 나쁩니다. URL 변경은 배포 전 검증에 전부를 걸어야 합니다.
- **"크롤링됨 – 미색인"이 지배적이면 기술 SEO를 그만 파세요.** 그건 콘텐츠 판정입니다. canonical을 백 번 다듬어도 안 바뀝니다.
- **렌더링된 HTML만 믿지 마세요.** `curl -sI`로 응답 헤더까지 봐야 검증입니다.

### 자주 묻는 질문 (FAQ)

**Q. 색인이 갑자기 0이 되면 가장 먼저 뭘 봐야 하나요?**
A. 서치 콘솔 색인 보고서의 '사유' 분포입니다. robots 차단·리디렉션 오류·서버 오류가 지배적이면 기술 문제라 고치면 됩니다. "크롤링됨 – 현재 색인이 생성되지 않음"이 지배적이면 품질 판정이라, 고칠 대상이 코드가 아니라 콘텐츠입니다.

**Q. 리디렉션 오류는 원인을 고치면 저절로 사라지나요?**

**Q. 그래서 지금은 회복됐나요?**
